# Контракты сценариев HUB_Optimus

> **Статус перевода: `review-needed`.** Этот текст является проектом перевода
> без подтверждения квалифицированной лингвистической проверки человеком.
> Каноническим источником для этой поверхности управления является
> [английская версия](../../governance/SCENARIO_SCHEMA.md).

## Назначение

HUB_Optimus намеренно разделяет два разных контракта сценария:

1. подробный шаблон человеческого рабочего процесса для структурирования
   анализа и проверки; и
2. строгий исполняемый JSON-ввод, принимаемый прототипом симулятора.

Это связанные поверхности авторской работы, а не эквивалентные представления.
Преобразование человеческого рабочего процесса в исполняемый JSON — ручное
решение моделирования с потерей информации. В репозитории нет автоматического
конвертера, а принятие исполняемого ввода не проверяет ни человеческое
описание, ни какие-либо утверждения о реальном мире.

## Исполняемый контракт JSON

Корневой объект содержит ровно пять обязательных полей. Неизвестные поля в
корне и внутри `roles[]` отклоняются.

| Поле JSON | Допустимая форма | Текущее использование загрузчиком/runtime | Чего это не означает |
|---|---|---|---|
| `title` | Непустая строка, состоящая не только из пробелов | Сохраняется в объекте runtime `Scenario`. Сейчас не влияет на действия участников или успех. | Идентификатор рабочего процесса, версия, запись доказательств или проверенное название из реального мира. |
| `description` | Непустая строка, состоящая не только из пробелов | Сохраняется в `Scenario`. Текущие встроенные политики его не читают. | Структурированный контекст, хронология, проверка истинности или оценённое повествование. |
| `roles` | Непустой массив; каждый элемент содержит только непустые строки `name` и `role` | Загрузчик требует уникальности значений `name`. `name` идентифицирует участника и его запись в истории. `role` передаётся выбранной политике; текущая политика `biased` особо обрабатывает точные значения `hardliner` и `mediator`, а политика по умолчанию и прочие значения роли используют равномерные предложения. | Цели, ограничения, полномочия, обязанности по проверке, биография или объявление отдельной политики для участника. |
| `success_criteria` | Непустой объект со строками, числами, целыми, логическими значениями или JSON `null` в качестве значений | После каждого раунда успех наступает, когда любое действие любого участника совпадает с любой одной парой ключ/значение критерия. Поэтому критерии имеют семантику OR, а не AND. Текущие встроенные политики создают только `offer`. Ядро сравнивает `actor_action.get(key)` с ожидаемым значением, поэтому критерий `null` также совпадает с действием, где этот ключ отсутствует. | Человеческое определение минимального или расширенного успеха, проверка, долговечность, стабильность или качество политики. |
| `max_rounds` | Целое число не меньше `1` | Задаёт максимальное число раундов. Если до предела не совпал ни один механический критерий, возвращается неудача. | Повестка раундов, последовательность, срок, план переговоров или гарантия выполнения всех запланированных раундов. |

Исполняемые файлы должны быть стандартным JSON. YAML и нестандартные константы
`NaN`, `Infinity` и `-Infinity` не принимаются. Проверка схемы и идентичности
подтверждает только целостность ввода, но не фактическую точность.

## Сопоставление с подробным человеческим рабочим процессом по полям

| Раздел человеческого рабочего процесса | Возможная ручная проекция в JSON | Только повествовательное содержание или отсутствие в runtime |
|---|---|---|
| **0. Метаданные** — ID, версия, язык, дата обновления, автор, статус | Человек может выбрать краткое отображаемое значение для `title`. Автоматического выведения нет. | Версия, язык, даты, авторство, статус рабочего процесса и история изменений не имеют исполняемого поля. |
| **1. Краткое резюме** — ситуация, минимальная цель, источник сложности | Краткое описание контекста можно вручную записать в `description`. | Runtime хранит, но не оценивает резюме, цель, сложность или их фактическую основу. |
| **2. Участники и роли** — стороны, третьи лица, цели, пределы, давление | Идентификаторы участников и краткие метки ролей можно перенести в `roles[].name` и `roles[].role`. Имена должны быть уникальными. | Цели, пределы, внутреннее давление, полномочия и отношения не имеют исполняемого представления. Дополнительные ключи внутри роли отклоняются. |
| **3. Контекст и хронология** — предыстория, недавние события, горизонт | Выбранный контекст можно вручную сократить в `description`. | События, даты, временные связи, вехи и временные горизонты не моделируются. |
| **4. Интересы, позиции и ограничения** — интересы, требования, внутренние ограничения, красные линии, гибкость | Прямой проекции нет. | Все поля этого раздела остаются повествовательными. Их нельзя добавить в `roles[]` без изменения схемы. |
| **5. Минимальная цель и критерии успеха** — минимальный успех, расширенный успех, явная неудача | Только критерий, который можно выразить ключом действия и скалярным значением JSON, может быть вручную записан в `success_criteria`. | Человеческое качество результата, расширенный успех, явная неудача, долговечность и проверка не оцениваются. Несколько записей JSON являются альтернативами, а не конъюнкцией. |
| **6. Начальное предложение** — действие, график, география, исключения, проверка, меры при нарушении | Прямой проекции нет. | Текущий JSON не может предварительно задать предложение, график, географию, исключение или меру принуждения. Встроенные политики создают простые действия `offer` во время исполнения. |
| **7. Проверка и соблюдение** — проверяющий, предмет, метод, частота, доступ, споры | Прямой проекции нет. | Симулятор не интегрирует доказательства, датчики, контроль доступа, соблюдение, разрешение споров или Trust Layer. |
| **8. Риски и точки трения** — недопонимание, стимулы к обману, неоднозначность, саботажники, инциденты | Прямой проекции нет. | Текущий runtime не обрабатывает риски, причинную или враждебную динамику. |
| **9. Рекомендуемые раунды** — этапы, проект соглашения, открытые вопросы, следующие шаги | Человек может выбрать `max_rounds` как механический предел. | Содержание этапов, последовательность, результаты, открытые вопросы, ответственность и сроки не исполняются. |
| **10. Итоговая оценка** — ясность, проверяемость, осуществимость, политическая цена, риск эскалации | Проекции во входные данные нет. | Поля результата `status`, `rounds`, `history` и `detail` являются механическими данными запуска и не вычисляют эти оценки. |
| **11. Метаобучение** — уроки, ошибки, отсутствующие определения, будущие изменения, новые вопросы | Прямой проекции нет. | Runtime не обновляет сценарии, не учится по результатам запусков и не создаёт выводов управления. |

## Связь с облегчённым авторским шаблоном

[`../../scenarios/scenario_template.md`](../../scenarios/scenario_template.md)
помогает предлагать и проверять материалы в репозитории, но не является
входным файлом симулятора. Название, краткий контекст, метки участников и
механически выражаемое условие успеха могут вручную повлиять на `title`,
`description`, `roles` и `success_criteria`. В шаблоне нет отдельного поля
`max_rounds`; исполняемый предел нужно выбрать отдельно. Семейство сценария,
напряжение, режим неудачи, инварианты, план бенчмарка и заметки не имеют
прямого поля runtime. Предложение бенчмарка не становится зафиксированным
бенчмарком только из-за наличия исполняемого JSON.

## Средства управления runtime не являются полями сценария

Поддерживаемая CLI предоставляет средства управления вне документа JSON:

- позиционный путь сценария или `--scenario` выбирает входной файл JSON;
- `--seed` выбирает воспроизводимый случайный поток;
- `--policy` выбирает одну поддерживаемую политику для всех участников
  (`uniform` или `biased`); и
- `--output` выбирает путь результата.

Человеческие стратегии для отдельных участников, доказательства, правила
проверки и этапы переговоров нельзя закодировать добавлением этих имён в JSON.
Неизвестные поля отклоняются.

## Пример минимальной проекции

Человеческий рабочий процесс может описывать несколько сторон, интересы,
риски, меры защиты и проверенное соглашение. Следующая исполняемая проекция
сохраняет только две метки участников, одно механическое условие предложения и
предел в пять раундов:

```json
{
  "title": "Частичное прекращение огня",
  "description": "Две фракции ведут переговоры о частичном прекращении огня.",
  "roles": [
    {"name": "ФракцияA", "role": "negotiator"},
    {"name": "ФракцияB", "role": "negotiator"}
  ],
  "success_criteria": {"offer": 5},
  "max_rounds": 5
}
```

Успешный запуск означает лишь то, что хотя бы одно созданное действие
содержало `"offer": 5` до достижения предела. Это не означает, что прекращение
огня было согласовано, проверено, устойчиво, легитимно или целесообразно.

## Дисциплина изменений

- Не добавляйте в исполняемый JSON поля, предназначенные только для
  человеческого рабочего процесса; проверка их отклонит.
- Не описывайте человеческий шаблон как исполняемый, а JSON — как полный
  аналитический сценарий.
- Любое изменение исполняемого поля требует отдельного ограниченного изменения,
  которое одновременно обновляет `scenario.schema.json`, загрузчик/runtime при
  необходимости, примеры, тесты и документацию runtime.
- Более содержательный перевод человеческого процесса в runtime требует явно
  одобренной issue для схемы/runtime. Это сопоставление не предоставляет такой
  возможности.
